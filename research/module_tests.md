# Module — tests

The test harness of the R9700 vLLM tuning toolkit: the runner, the assertion file, the fixtures, the stub executables, the static checks, the document checks and the CI workflow. It tests every verb of `bin/r9700` against stubs of `wslc` and Windows PowerShell: no container, no GPU and no real vLLM server is started, and nothing is written outside one owned run folder. Where a flow needs the GPU it is a `not covered` row of the catalogue with its acceptance record. Every test file runs in the same runner; there is no second one.

The runner lowers its own priority first (`tests/lib/lower-priority.mjs`), so every child inherits it; it runs one file at a
time (one worker, below the cap of 8) and gives each file a ceiling of 10 minutes, after which the child's whole process
group is killed. It starts every child from an argv array, never a shell string. CI throttles nothing.

## The process cap

Why: on 2026-11-02 a test shim for `python3` found itself first on `PATH` (the second call of its helper looked the tool up and found the shim) and exec'd itself without end:
about 15,900 processes, a crashed session. So no test file runs unguarded any more.

- `tests/run.mjs` starts every file as `bash -c 'ulimit -u <cap>; exec <command>'`. The cap is the user's THREAD count at the start of the run (Linux counts the threads of the
  whole user against `RLIMIT_NPROC`; `ps -L -u <uid> | wc -l`) plus `R9700_TEST_NPROC_HEADROOM` (default 3000), never above the hard limit the runner itself has. The runner
  prints `run: process cap <n> …` first.
- It also watches the file's own session every 0.4 s. When the session's threads reach half of the headroom (the other processes of the user may grow while the file runs, so the kernel limit alone could come first; no test file keeps anywhere near that many threads) it prints `process cap reached (<n>): a test forks without end`,
  stops and then kills every member of that session (round after round: a fork loop keeps making members while it is killed), and the file FAILS (`FAIL <file> (process cap
  reached (<n>))`, the run exits 1). Only the file's session is signalled, never another process. The kernel limit is the backstop: a file that forks past it gets `EAGAIN`.
- Proved by `tests/test_runner.sh` with `tests/fixtures/runner/test_forks_without_end.sh` (a folder the normal suite never lists; the runner is pointed at it with
  `R9700_RUNNER_TESTS_DIR`): FAIL within seconds, exit non-zero, the user's thread count back to its start value. The fixture refuses to run without a cap.
- Run every test command under an outer guard as well, so a bug in the runner itself is contained: `bash -c 'ulimit -u $(( $(ps -L -u $(id -u) --no-headers | wc -l) + 3000 )); exec nice -n 19 node tests/run.mjs <file>'`.
- **Rule for every test shim: a shim never resolves to itself.** Look the real tool up with the shim directory removed from `PATH` (`PATH="${PATH//"$dir:"/}" command -v python3`), refuse a
  result inside the shim directory, and put the directory on `PATH` once however often the shim is written.

## Test leftovers

Every test file writes only inside ONE folder per run, `testsToDelete-<owner>-r9700-run-<id>`, which `tests/run.mjs` claims,
creates and removes; pytest gets a subfolder as `--basetemp`, a bash test gets its own as `R9700_TEST_ROOT`. No test makes a
temp path of its own and none changes the temp-folder environment variables. A run killed with `kill -9` leaves its folder;
the next run's sweep lists it as `removed` once the folder is more than 10 minutes old (the sweep's age selector) and its
owner process is gone. A test that records the pid of a process outside every process group writes it to
`$R9700_TEST_ROOT/containers/<name>.pid`; the EXIT trap of `run_all_tests` (`kill_recorded_pids`, searching every `containers/` folder below the test root) and the
runner's `finally` kill every recorded process before the folder is removed (E1.S2 amendment A4; S1 builds the two killers, S2
writes the stubs that record). A record is `<pid> <start ticks>` (field 22 of `/proc/<pid>/stat`, read after the last `)`); a pid
is killed only while it still has those ticks, so a reused pid is never killed; `record_pid <file> <pid>` writes the record.
SIGINT, SIGTERM and SIGHUP make the runner end the current file's process group AND its whole session (every process whose session id is the file's own pid; GNU `timeout` gives its child a process group of its own but not a session, so a stub call is outside the group and inside the session; the same at the 10-minute ceiling and after every file ends, so a passing file cannot leave a disowned subshell behind). The runner records the child's start ticks at spawn and skips a group or session kill when a process with that pid has other ticks (a reused pid), kill the recorded processes, remove the run
folder, print one `run: interrupted (<signal>)` line (no FAIL line, no summary) and exit 130, 143 and 129. A closed output pipe
(`node tests/run.mjs | head -3`) is handled the same way, silently, with exit 141; a test file ended by a signal is reported as
`FAIL <file> (signal <name>)`. A test that starts a process outside every group also records it with `guard_pid <pid> <name>`
(its real start ticks, in `$R9700_TEST_ROOT/guard/containers/`, a folder no killer under test is given), so the EXIT trap and the
runner end it on every path; `gone <pid>` polls until a process is gone.

## What it does not prove

- **The stub's foreground container is listed and stoppable like a detached one.** LISTED: observed on the real `wslc` on 2026-11-04 (09:16–09:24 UTC): during a real `moe-tune chunk` (a foreground `run --rm --name r9700tune-moe-tune-…`) a watcher beside it saw the name in `wslc list` every 10 s (the short list cuts the name; the toolkit lists with `--no-trunc`). Whether it is STOPPABLE by name was not exercised that day (run 1 of the `run` acceptance stopped a detached server by name). The guards stop a chunk container by name AND end the worker's session, so the unit is ended either way, but the acceptance run of the MoE story watches a real `wslc list` during a chunk.
- **The tuning itself never runs.** The stub answers `benchmark_moe.py` with a scripted file; the vendored benchmark, the Triton cache and the real timings are not exercised, and the cache volume is never touched (the clear container is a stub).
- **The default arm's `Using …` line for a folder without the file is unknown.** It is recorded as `A_CONFIG_LINE` and never judged; the text the fixture shows is `Using default MoE config…`, seen in a server log, not in the benchmark's.
- **The hung hook is hung by the stub, not by a wedged `wslc.exe`.** T12 and T19 prove the supervisor's window and tree kill against a stub that ignores `TERM` (and one that obeys it); a Windows process that survives `KILL` of its WSL parent is still the E1 UNVERIFIED assumption. Because `_rg_tree_kill` sends the group `KILL` right after `TERM`, the test cannot tell which signal ended a hung call that obeys `TERM`.

- **The stub writes the quality files the container would.** In the series tests the `harness.py` calls (`collect`, `gsm8k`) are answered by the
  `wslc` stub, which writes a 20-result file and a GSM8K summary of n 200 under the work directory; the real `lib/harness.py` runs against a
  real server only in the acceptance run. The same holds for `vllm bench serve`: the stub prints the recorded fixture lines.
- **The model listing and the generation-config hashes are stub answers.** The program the throwaway container runs is run for real in F7 and F8
  (nested and hidden files, a path with `;` and `#`), but not inside the real image: whether `find -printf`, `xargs -r` and `sha256sum` exist
  there, and whether the image runs `sh -c` without an entrypoint that eats it, is found on the machine. The fingerprint hashes names and sizes of
  the model's files, not the weights: a same-size edit of a weight file is not seen (decision 1).
- **The 27B model file runs as a dry run in the acceptance**, not as a measurement: the dry run proves the resolved commands, not that the model
  serves at those settings.
- **The time scale shapes the S12 numbers; S13 does not race the clock.** S12's margins are measured against a deadline that is whole seconds; a machine slower than
  the one it was tuned on can move an arm-round across one. S13 and the direct test of `_series_gate` read a fake clock (see their row), so they stay true on a starved CPU and prove nothing about real elapsed time.

- **The benchmark never runs under `moe-tune` in CI, and hook 3 is unobserved until a draft chunk runs on the machine.** `moe-tune` is proven with the stub's scripted answers; the foreground-container listing (above) is a stub assumption, and `activate`'s refusal rests on it: a real `wslc list` that does not show a foreground container would let an activation through while a chunk runs (the lock still stops it while a `moe-tune` run holds it).
- **`activate` cannot see what a container mounts.** It treats every listed server or prefixed container as a reader. A server that is not listed but starts right after the swap reads the new file, as intended; one started by hand under another name with the folder mounted is not seen (`--force` is the operator's word in the other direction).
- **The vendored benchmark is never run in CI.** `tests/test_vendor.sh` proves it is upstream plus the three marked changes; it does not prove the changes work. Hooks 1 and 2 were observed
  in the 2026-10 work and hook 3 is known by its effect only (the B1 draft-layer chunks); none is observed through the toolkit until the acceptance run of the MoE story (`vendor/README.md`, *Verified on the machine*).
- **`merge` and `decide` are proven on the files of the published runs, not on a new chunk.** A chunk file made by a newer vLLM may hold other fields or another key order; `check` accepts extra fields and
  the merge keeps each config's own order, but only the real run shows the real file.
- **The atomic write rests on `os.link`.** M17 proves no overwrite and no half file on this filesystem; a results folder on a filesystem without hard links uses the fallback: a `<NAME>.claim` taken with `O_EXCL`, then check and replace. Tests force the fallback (a live claim refuses, a dead one is swept); it is not observed on such a filesystem.

- **The benchmark and the prefix requests never run in CI.** `lib/linear_bench.py run` imports torch, triton and vllm and needs the GPU; `linear-bench` is proven with the stub's scripted answer (the published fixture's rows for the config's shapes), and `prefixtest` against a local HTTP server and a stubbed `wslc exec`. Whether the port of the benchmark (`linear_bench.py` and `linear_bench_graph.py` merged into one file with the timer as an argument) measures what the two originals measured is observed only in the acceptance run on the R9700. The eager timer is kept as an option but its numbers are not a decode time (results § 11.3: the default path summed to 23.8 ms per forward against a decode step of 8.5-8.9 ms).
- **Whether the 27B AWQ model takes the hybrid W4A16 kernel is not known**, so its model file leaves `LINEAR_SHAPES` empty and `linear-bench` refuses it; nothing tests a measurement for it.
- **The prefix check records numbers, not a verdict.** `summarize` prints the cold and hit times and their ratio; no threshold is applied (measured before recommended). The 12 s stall of results § 6.1 is a cold-request measurement that may or may not appear.
- **A foreground linear container is stoppable by name** is the same stub assumption as for a chunk (above): the real `wslc` is not observed.

- **No GPU, no real `wslc`, no real vLLM server.** `lib/harness.py` is tested against a Python `http.server` stub on
  `127.0.0.1` that answers the two routes with fixed bodies; the real server's logprobs and chat template are not exercised.
- **The stubs are our idea of `wslc` and PowerShell, not theirs.** `wslc list` is assumed to print a header line and the container name as
  the last column (the old scripts' `awk 'NR>1{print $NF}'`); `run`, `logs`, `exec` and the PowerShell answers are scripted. A real
  `wslc` that prints another shape is found only on the machine.
- **The readiness program runs against a fake `urlopen`.** `tests/test_adapter.sh` runs the adapter's Python program under `python3` with
  `urllib.request.urlopen` replaced, so its logic and its output are tested (both checks, the status, the exception class), but no HTTP
  request is made; the first run on the R9700 closes that gap.
- **The worker's readiness program (`wait_ready_probe_program`) runs against a fake `urlopen` too**, in `tests/test_steps.sh`: its 200 and non-200
  paths and the route and the 5 s timeout it asks for are tested; whether the real server's `/v1/models` answers 200 on loopback port 8000 inside
  its container is found only on the machine.
- **The signal rules are proven for the supervisor's own waits, the admission calls and the worker, not for every call.** A `TERM` ends a quiet
  wait and an admission call at once; the restore inside a run and the readiness sleep are foreground commands, so a signal there waits for the
  current call (at most its ceiling) before the handler runs. A terminal's `Ctrl-C` goes to the whole foreground group and ends them at once; a
  `kill -TERM <pid>` of the supervisor alone is the case that waits. The tests send `TERM`, `HUP` and, through a python launcher that resets the
  ignored `SIGINT` of a background job, `INT`.
- **The time scale shortens sleeps and deadlines, not the kernel.** The tests run ten minutes as six seconds; the arithmetic is proven, the
  behaviour of a ten-hour night is not.
- **A test window is a production window divided by the time scale; the CPU time of a stub call is not.** A test that expects readiness gets a window the CPU cannot use up in practice: the restore tests' marker 33 s, the chain tests' `READY_TIMEOUT_S` 32 s, a `wslc list` ceiling of 30 s (`lc_setup`, `run_setup`), proven with no load by a stub call slower than the OLD window and faster than the new one (restore, `ready_wait`, chain: red on the old number, green on the new). A test whose subject IS a window or a deadline that runs out keeps a short one and stays exposed to a starved CPU; the load runs of 2026-11-05 are the evidence for the rest, not these tests.
- **The activation-dtype tests prove the argv and the record, not the kernel.** That the hook `MOE_TUNE_ACT_DTYPE=bfloat16` changes the activations the real benchmark tunes with is known from the draft-layer chunks of 2026-10-28..31 and has not been observed through the toolkit for the experts layer (`vendor/README.md`); no GPU run was made for this change.
- **The adapter's ceilings are proven on a hung stub**, not on a hung `wslc.exe`: `timeout` ends the stub and its children with `TERM`, and the stub itself with `KILL` after the grace (GNU `timeout` sends the second signal to the child only: a grandchild that ignores `TERM` survives. Whether `wslc.exe` has such children is an UNVERIFIED ASSUMPTION: nobody has observed it either way). The calls the supervisor makes itself are stopped by session (amendment A8) in E1.S2 part (b), which covers a hung adapter call under a guard stop. A Windows process started through WSL interop may need more than a signal to end.
- **The stubs refuse what we know the real `wslc` refuses** (exec and logs on a container that is not running, a second run of a name in use); the exact error texts of the real one are not known.
- **No Windows.** The static checks and the runner are exercised on Linux only. The path and priority code of the runner is
  shared with other repositories, where Windows is covered.
- **The verdict is checked against recorded runs, not against a new measurement.** The three recorded verdicts (`fcombo`
  passes, `fb1` and `o7` fail) are reproduced from the stored lines; whether the rule itself is the right rule is a design
  decision of the plan, not a test result.
- **The config loader checks shape, not meaning.** It cannot know that a Windows path names the same folder as its WSL
  twin, or that an image reference exists in a registry.
- **The leftovers guard is red on the token row until the token is released** in the shared rules (the `## Tokens` table of the
  mounted detail rule); it is expected to name only that row.

- **`run` chains stub steps, not real containers.** R1-R23 (with R3b, R5b, R18b and R20d) drive the real verbs against the `wslc` stub, and R3 and R17 put a stand-in worker in the place of a verb's body to test the CHAIN (the repeat after an exit 3, the mapping of every outcome to one exit code); a chain over real servers and a real restore was the acceptance run of E3.S3 (`research/ACCEPTANCE_run_2026-11-03.md`, run on 2026-11-03 with a forced RAM limit; a real RAM dip did not occur in it).
- **The busy-wait restore between steps is proven with the stub's load file.** R18 turns the load busy at the end of each step and quiet after each restore; whether a real PC's load behaves like that is the acceptance's question.

- **The document checks prove the shape, not the claim.** `tests/test_docs.sh` proves that every old script has a row, that its home exists and that a named verb is a verb; it does not prove that the home does what its note says (the notes were read against the old files by hand on 2026-11-03). It proves that an acceptance record has a prediction before its observed sections, that a record whose title says NOT RUN keeps empty prompts and that a record whose title says RUN holds no prompt or placeholder (the planted records of DOC13 come from the fixture `tests/fixtures/static/acceptance_template.md`, a NOT RUN template, because every real record is filled in now); it does not compare a prediction with a run: each record's own table does that, and a reader checks it.
- **The predictions of the acceptance records come from the results document and the stubs; the observed sections are what the real GPU, `wslc` and image did on 2026-11-03.** Several predictions did not hold (the tables say which): the cells of `linear-bench` at M 6 to 16, the wall time of the run record (35 to 40 minutes, which counted two quiet waits that were off by the operator's decision), the cache size before the A/B.
